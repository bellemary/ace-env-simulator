# ACE 客户端环境检测模拟器 — 检测原理与限制说明

**版本**：v2.6
**定位**：本地化 ACE 反作弊 SDK 环境检测模拟工具，不对接任何外部服务器

---

## 一、检测原理

### 基础模式 — 客户端环境探测模拟

基础模式不读取目标进程内存，而是逐项模拟 ACE SDK 在游戏运行过程中对客户端环境执行的探测步骤。每项检测独立运行，输出与游戏内 ACE 判断逻辑一致的结果（通过 / 可疑 / 高风险）。

覆盖检测项：

- Root 探测链（8 槽 OR 聚合 + manager_flag + unlock_root）
- Bootloader / Verified Boot / OEM Unlock 状态
- SELinux 状态与 enforce 模式
- 开发者选项 / ADB 调试状态
- 系统属性一致性指纹（Build.* 字段交叉校验）
- 厂商属性与启动历史 / 分区校验
- 虚拟管道 / 云手机 / 模拟器制品检测
- 风险包名 / 多开框架 / Xposed 类框架环境
- Keystore 认证 / MediaDrm 设备身份

每项检测在 UI 中展示四要素：**检测项目名称** → **检测详情**（检查的路径 / 属性 / 系统调用）→ **模拟结果** → **对用户环境的最终影响**。

### 高级模式 — 内存特征 + ano_tmp 解密

高级模式需要 Root 权限，流程为：自动启动游戏 → 持续扫描内存特征点 → 用户手动结束 → 扫描 ano_tmp 目录并逐一解密。

**内存扫描**：通过 `/proc/[pid]/maps` 实时解析模块基址（支持 ASLR），使用 `process_vm_readv` 读取每个特征点至少 64 字节，与安全环境基线对比后判定正常 / 可疑 / 异常。

**ano_tmp 解密**：覆盖以下文件族的已知格式：

| 文件族 | 容器 | 解码方式 | 完整性校验 |
|--------|------|----------|------------|
| ano_rdp.dat | BE32 头 + XOR | ANO_KEY XOR | 32 位十六进制摘要 |
| kvcache8.dat | LE32 头 | ANO_KEY XOR | CRC32 尾部校验 |
| mrpcs_a_v.data | ZIP + XOR | [4,EOF) XOR 0x4F | LE32 CRC32 |
| mrpcs_a_v_f.data | ZIP + XOR | [4,EOF) XOR 0x84 | LE32 CRC32 |
| mpmc.dat | LE32 头 | 结构化字段 | CRC32 校验 |
| comm.dat / comm.zip | XOR + ZIP | ANO_KEY XOR | 字段名校验 |
| config2/3.dat.* | BE32 头 + XOR | ANO_KEY XOR | magic 校验 |
| ano.ano3.dat | LE32 头 | 结构化字段 | 尾部 magic 校验 |
| h_rcd.dat | LE32 头 | 固定字读取 | magic 校验 |
| tersafe.update | 无容器 | 结构化字段 | magic 校验 |
| ace_shell_db.dat | BE32 头 | 大端字读取 | magic 校验 |

所有解码均通过 CRC32 或 magic 校验确认密钥正确性，不存在「猜测密钥」的情况。

## 二、已知限制

### 1. 解密结果因设备而异，无法用固定格式解读

ano_tmp 目录下的文件是 ACE SDK 在运行时采集的**设备环境画像**。不同设备的解密结果必然不同：

- `ano_rdp.dat`：32 字节十六进制设备指纹摘要，每台设备唯一
- `kvcache8.dat`：键值对缓存，包含 `vm_app_ver`、`mem_ava`、`is_history_x86` 等运行时状态
- `mrpcs_a_v.data`：规则能力镜像，包含 `libUE4.so`、`libtersafe.so`、`/data/adb/ksud` 等检测目标路径
- `comm.dat`：通信配置，包含 `frida_scan`、`anti_profiler`、`rootkit_ver` 等策略开关

因此，**软件无法用一个固定的格式内容去解读所有设备的解密结果**。软件提供的是解码能力（将密文还原为明文），而非对明文内容的统一判定。

### 2. 明文解读需人工或 AI 介入

解密后的明文包含设备特定的指纹、路径、状态值。要判断这些值是否构成风险，需要：

- **人工查看**：对照 ACE 已知检测逻辑（如 `frida_scan=1` 表示 ACE 会扫描 Frida 痕迹），逐项判断
- **AI 辅助分析**：将解密明文交给 AI，结合 ACE SDK 逆向结论推断环境特征

软件内置的「智能解释」仅提供文件级概述（文件作用、ACE 检测中的角色、为何被采集），不针对具体字段值给出设备级风险判定。

### 3. 手动压缩包已排除

以下文件为手动创建的状态归档，非游戏生成，软件已自动跳过不解码：

- `ano_tmp.zip` / `ano_dfh.zip`
- `大厅.zip` / `对局.zip` / `大厅前.zip`

### 4. 其他限制

- 高级模式需要 Root 权限（`id -u == 0`）
- 内存扫描需目标进程存活且 `libtersafe.so` 已加载
- 单轮总读取上限 64 MiB，单文件上限 8 MiB
- 最多处理 256 个不重复文件

---

## 三、使用建议

1. **基础模式**用于快速评估环境是否会被 ACE 判定为异常（不依赖 Root，不读取目标进程）
2. **高级模式**用于获取 ACE 实际采集的设备画像明文，配合人工或 AI 分析具体风险点
3. 高级模式结果自动保存至 `/storage/emulated/0/ACE解密结果/ACE_Result_YYYY-MM-DD_HH-mm-ss.txt`
4. 如需深度分析，建议将解密明文连同内存特征点报告一并提交给 AI 进行综合判断

---

*本工具仅用于环境检测模拟与安全研究，不修改目标进程内存，不对接外部服务器。*
